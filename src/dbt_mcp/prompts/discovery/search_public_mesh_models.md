Searches for public dbt Mesh models across producer projects and confirms each producer's identity, returning the exact cross-project `ref` and `dependencies.yml` entry.

**Scope:** only models with Mesh `access: public`, and only the projects named in `project_ids` (which must be a subset of the configured project IDs). Private and protected models are never returned — use `get_node_details` to inspect a specific model regardless of access level. To audit your *own* project's public interface, use `get_all_models` instead; it lists the bound environment's public models with no cross-project search. Follow up with `get_node_details` on any of them for `group`, `contractEnforced`, and the rest of a model's governance config.

**Identity verification is automatic.** For each project, the tool asks the platform for that environment's own `dbt_project.yml` name rather than guessing from a model's `unique_id`. Only a model whose namespace matches is returned, with `dbt_project_name` and `ref` populated. A project whose *own* identity lookup fails lands in `coverage.failed` instead, since none of its nodes could be attributed to it at all.

**Two ways to search:** `query` (text search over names/descriptions) and `relation_name` (exact warehouse relation lookup, matched right-aligned against each model's `database`/`schema`/`identifier` — `fct_orders`, `gold.fct_orders`, and `prod.gold.fct_orders` are all accepted). See each parameter's own description for matching rules. Supplying `relation_name` narrows each project to that one relation server-side, before `query` applies; a `query` alongside it can only exclude that single model from `models`, never broaden the search or affect `lookup`. Because `relation_name` matches the warehouse identifier rather than the dbt model name, it finds aliased and versioned models that `query` misses. Omitting both returns every public model in scope.

**Returns** a `MeshModelSearchResult`:
- `models` — matching public models, each with `model_name`, `unique_id`, `package_name`, `version`, `latest_version`, `last_run_status` and `last_run_generated_at` (raw passthrough from the platform's last run, null when unavailable — no staleness logic applied), `project_id`, `relation_name`, `dbt_project_name`, and `ref` (the ready-to-use `{{ ref(...) }}` string). Pass `project_id` with `unique_id` to `get_node_details` for anything else about a model. A node the platform confirms belongs to a *different* project (an installed package, say) is excluded entirely.
- `coverage` — `searched`, `failed` (project → reason, including an identity-lookup failure), `incomplete` (scan stopped with pages remaining), and `models_scanned` (`null` on a `relation_name` lookup, which is a point query rather than a scan).
- `lookup` — present only with `relation_name`: the echoed relation, `found`, and `conclusive`.
- `dependencies` — one producer project name per entry, deduped, in first-seen order — exactly the `dependencies.yml` list.
- `omitted_model_count` — how many matches `limit` cut.

**Reading `lookup` correctly.** `found: false` is only authoritative when `conclusive: true`. A negative is undermined by any project in `coverage.failed` or `coverage.incomplete`. A *private or protected* model at the relation yields `found: false`, which is correct (it isn't ref-able) but still means the developer is about to source over a dbt-managed relation. And `conclusive: true` means "not claimed by a project in `project_ids`", never "not claimed by any dbt-managed model" — use `get_node_details` for that. Before declaring a new source, make sure every candidate producer is in `project_ids`, then require `conclusive: true`.

**Sizing.** `models` is capped at `limit` (1-100, default 50) across all searched projects — a cap on the merged list, not a GraphQL page, and there is no cursor for more. A nonzero `omitted_model_count` means you should narrow with `query`, `relation_name`, or fewer `project_ids` rather than raise `limit`, which just moves the same cliff. `lookup`, `coverage`, and `dependencies` are all computed over the full scan before truncation. Within a project, results are ordered most-queried first; the merged list concatenates projects in `project_ids` order, so truncation cuts from the end — a project late in `project_ids` can contribute nothing to `models` while still appearing in `dependencies`.
